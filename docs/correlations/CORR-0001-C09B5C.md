# CORR-0001: ROMCPU:$C09B5C

First static/runtime correlation under `docs/static-analysis/GHIDRA_MESEN_WORKFLOW.md`.

## Status

- State: correlated
- Confidence: mixed — per claim, see [Correlation](#correlation). The routine's
  **mechanism** is Confirmed. Its **semantic role** ("event-script pointer")
  remains a Strong hypothesis.

## ROM identity

- SHA-256: `0f51b4fca41b7fd509e4b8f9d543151f68efa5e97b08493e4b2a0c06f5d8d5e2`
- Header status: no copier header (3,145,728 bytes ≡ 0 mod `0x8000`)

## Address mapping

- Canonical CPU address: `ROMCPU:$C09B5C`
- Ghidra address: `c09b5c`, block `bank_c0_hirom` (`c00000-c0ffff`, r-x, initialized)

## Research question

Does execution reach exactly `ROMCPU:$C09B5C`; in what 65816 state; what does it
actually do to the direct-page operands `$E5-$E7` and `$E3`; and what is its
real control-flow relationship with `ROMCPU:$C09A6D`?

## 65816 processor state

Measured at the entry PC on every one of 24 observations (12 hits × 2 runs).
**Invariant across all 24:**

| Field | Value | Source |
|---|---|---|
| E (emulation) | `false` — native mode | `CpuState.emulationMode` |
| M (accumulator width) | `1` — **8-bit A** | P bit `$20` |
| X (index width) | `0` — **16-bit X/Y** | P bit `$10` |
| PBR | `$C0` | `CpuState.k` |
| DBR | `$00` | `CpuState.dbr` |
| DPR | `$0000` | `CpuState.d` |
| SP | `$15FD` | `CpuState.sp` |

Source of state assumptions: **none remain assumed.** Every value above was
read from the live CPU at the entry PC rather than inferred. P varied across
hits (`$20/$21/$60/$61`) but the M and X bits did not.

Because DPR = `$0000`, the direct-page operands resolve to:

| Operand | Effective CPU address | WRAM |
|---|---|---|
| `$E3` | `$0000E3` | `WRAM:+$00E3` |
| `$E5` | `$0000E5` | `WRAM:+$00E5` |
| `$E6` | `$0000E6` | `WRAM:+$00E6` |
| `$E7` | `$0000E7` | `WRAM:+$00E7` |

This matters: every prior direct-page read in this project hardcoded D = 0.
That assumption is now **measured** at this site, not inherited.

1. **Entry is exact.** The reported PC equalled `$C09B5C` on all 24
   observations (`targetMatch=true`).
2. **The delta equals `A & $FF` on all 24 observations**, and the value varied
   across 1, 2, 3, 4, 5, 7.
3. **Control always reaches `$C09A6D`**, in the same frame, on all 24.
4. **`$E3` behaviour.** When `$E3` was `$00` at the continuation, the bypass
   path `$C09A75` executed. When `$E3` was `$1E` (30), the wait path
   `$C09A71` executed **once per frame for exactly 30 consecutive frames**
   (hit 2: frames 18950-18979; hit 6: frames 18981-19010), then the bypass ran
   on the next frame. Twice, exactly.
5. **Entry is not exclusive to the flag handlers.** A flag-family handler
   (`$C0B5F4`) executed in the same frame for only hits 4-6. Hits 1-3 had no
   flag handler execute at all, and the flag handlers always load `#$02`, so
   the observed A values of 1, 3, 4, 5 and 7 cannot originate there.
6. **Null result, recorded.** A first run over frames 15,001-16,801 produced
   **zero** hits (`corr0001-obs0-shortwindow.log`). The routine does not run
   continuously; it runs in bursts while the script advances.

### Static cross-check of the deltas

Treating the observed before-addresses and deltas as a byte stream, the chain
is contiguous from hit 3 through hit 12 — `before + delta == next before` at
every step, with no gap or overlap. Splitting the ROM at those boundaries:

```
$CC9A56  len 3   F1 39 A0
$CC9A59  len 2   D3 CC
$CC9A5B  len 4   F6 82 00 FF
$CC9A5F  len 1   92
$CC9A60  len 4   00 82 D7 FF
$CC9A64  len 5   3C 00 0E 0F FF
$CC9A69  len 2   41 00
$CC9A6B  len 7   0E 85 D5 25 3C C2 FF
$CC9A72  len 7   0F 85 D5 27 3C C2 FF
$CC9A79  len 2   41 0E
```

Opcode `$41` appears twice, both times with length 2. `$0E` and `$0F` appear
as two 7-byte records differing in a single operand byte. This is what a
variable-length bytecode stream looks like, and the runtime deltas segment it
consistently.

## Correlation

| Claim | Confidence |
|---|---|
| Execution reaches exactly `ROMCPU:$C09B5C` | **Confirmed** |
| At entry: E=native, M=1, X=0, PBR=`$C0`, DBR=`$00`, DPR=`$0000`, SP=`$15FD` | **Confirmed** |
| DP operands resolve to `$0000E3` / `$0000E5-$0000E7` | **Confirmed** (follows from measured DPR) |
| The 24-bit LE value at `$0000E5-$0000E7` increases by exactly `A & $FF` | **Confirmed** (24/24, delta varied) |
| Control transfers to `ROMCPU:$C09A6D` immediately | **Confirmed** (24/24, same frame) |
| `$C09A6D` decrements `$E3` once per frame and takes the wait path until it reaches zero | **Confirmed** (two independent countdowns, exactly 30 frames each) |
| `$C09B5C` is a **shared tail** reached from multiple distinct command handlers, not only the flag family | **Confirmed** (A values impossible for the flag handlers) |
| `$C09B5C` is a routine entry, not an internal basic block | **Confirmed** — the preceding instruction is an unconditional `JMP ($002A)`, and every observed entry was by explicit transfer |
| The 24-bit value is an **event-script pointer into ROM** | **Strong hypothesis** |
| `$E3` is the **event-script frame-wait counter** | **Strong hypothesis** |
| A is the **command length** of the just-executed script command | **Strong hypothesis** |

The three hypotheses share one ambiguity, stated plainly: this pilot never
observed the value at `$0000E5-$0000E7` being *dereferenced*. The static
decode shows `LDA [$E5],Y` at `$C09B1E`, and the contiguity result is strong
circumstantial support, but "pointer" is an inference from arithmetic and
address range, not a measured dereference.

## Alternatives

1. **The 24-bit value is a cursor into something other than an event script**
   — a text stream, a DMA source list, an animation script. Not excluded: all
   observed values lie in ROM banks `$CA`/`$CC`, which this project has not
   yet characterised. The contiguity and the opcode/length regularity argue
   against a non-instruction stream, but do not settle which stream.
2. **A is not a "length" but an arbitrary per-handler constant** that happens
   to segment the data coherently. Weakened by opcode `$41` producing length 2
   on both appearances, and by `$0E`/`$0F` producing matched 7-byte records.
3. **`$E3` is a general-purpose frame counter** shared with a non-script
   subsystem, and its interaction here is incidental. Not excluded — this
   pilot only observed `$E3` at this one site.
4. **The invariant state (SP=`$15FD`, DBR=`$00`) is an artefact of the single
   starting state**, not a property of the routine. Both observations descend
   from the same milestone, so this is a real limitation, not a refuted
   alternative.
5. **`$C09B5C` might still be an internal block of a larger routine** whose
   entry lies elsewhere. Argued against by the unconditional `JMP ($002A)`
   immediately before it, but no caller-side boundary analysis was performed.

## Falsification result

The pre-registered falsifier was: *a constant delta, or a delta independent of
A, refutes the "amount comes from A" reading.*

**Not met — the reading survived.** Deltas varied across six distinct values
(1, 2, 3, 4, 5, 7) and matched `A & $FF` on 24 of 24 observations. A constant-
delta model is refuted outright.

A second reading was refuted along the way: that `$C09B5C` is *the flag
handlers' tail*. Nine of twelve hits had no flag handler executing, and five
distinct A values are unreachable from handlers that always load `#$02`. The
narrow reading implied by ROM-0027's notes is too small; `$C09B5C` is shared.

## Unresolved and deferred

**Unresolved processor-state assumptions:** none at the entry PC — E, M, X,
PBR, DBR, DPR and SP were all measured. What remains unmeasured is whether
those values are *invariant properties of the routine* or *properties of this
starting state*; both observations descend from the same milestone.

**Not established:** the immediate predecessor instruction per hit. The probe
recorded the last execution within the flag-handler range, which is not the
same as the instruction executed immediately before entry. The evidence
supports *multiple distinct predecessors*, but names none of them for hits
1-3 and 7-12.

**Constitutional note:** `CLAUDE.md` requires a falsifiable experiment record
under `docs/experiments/` before operating Mesen. This unit was scoped to
exactly one `CORR` record, so the design was pre-registered in this record's
[Runtime experiment](#runtime-experiment) section instead. Registering an
`EXP-NNNN` for the runtime half is available and would require a
`manifests/experiments.json` entry plus index regeneration.

**Deferred neighbouring leads** (observed, registered, *not* investigated):

- `ROMCPU:$C09B3B-$C09B5B` — an opcode dispatcher: bounds-checks against
  `#$31`/`#$35`, computes `(opcode − $35) × 2`, loads a pointer from
  `ROMCPU:$C098C4,X`, stores it to `$2A`, and dispatches via `JMP ($002A)`.
- `ROMCPU:$C098C4` — candidate opcode jump table; the first 64 entries are all
  plausible bank-`$C0` code pointers spanning `$C09C44-$C0A336`.
- `ROMCPU:$C09B1E` onward — reads six bytes via `LDA [$E5],Y` into `$EA-$EF`,
  then tests `$EA`. Supports the pointer reading but was not exercised here.
- `ROMCPU:$C09B82` — a third advance variant maintaining a 3-byte-stride
  structure at `$05F4` indexed by `$E8`; candidate script call stack.
- ROM banks `$CA`/`$CC` around `$CC9A55` — candidate event-script data.
